# Game identity map

This is the index for building stable identities across Banished's package data, Ghidra analysis,
and runtime object graph. The goal is to map every shipped resource and then connect paths, names,
type IDs, code addresses and object fields without confusing one kind of pointer with another.

## Resource inventory baseline

[`GAME-RESOURCE-INVENTORY.tsv`](GAME-RESOURCE-INVENTORY.tsv) lists every TOC entry from the four
original Windows data packages. It is generated by `python3 tools/pkg_inventory.py`; the generator
reads the package tables without extracting or changing payloads. For compiled resources it also
decodes the compressed container header and records the serialized type ID, uniquely matched class
name, file version and file-header dependency count. Each row records package name, package
priority, entry kind, normalized resource path, byte offset in the package and stored size.

[`GAME-RESOURCE-REFERENCES.tsv`](GAME-RESOURCE-REFERENCES.tsv) is the corresponding edge list for
the file-header dependency strings and their raw serialized FILETIME values. Generate both indexes
with:

```sh
python3 tools/pkg_inventory.py \
  -o docs/GAME-RESOURCE-INVENTORY.tsv \
  --references-output docs/GAME-RESOURCE-REFERENCES.tsv
```

| Package | Priority | Entries | SHA-256 |
|---|---:|---:|---|
| `data0.pkg` | 200 | 5,428 | `8e3064ee0d7c89f41ac2ba26beee046801d463030fb40a0710a01548bc01debb` |
| `data1.pkg` | 100 | 406 | `8016e16d0b9152752ee724f22f427d6634df13c0b8bae8f3d831b27b2aed6176` |
| `patch0.pkg` | 190 | 1 | `e694c96a89e8f92112998d0e6a3e012db84908ffffc5095a1d8b6bbc87d30163` |
| `patch1.pkg` | 120 | 1 | `6295ecec540b6fa72a2e9905b4997c313448328d502f0933396b8e1988990d39` |

Across these inputs there are 5,836 distinct TOC paths and no duplicate path strings. The rows
include 5,812 `.crs` compiled resources, 16 `.str` audio streams, four `.sav` entries and four
package-index entries. Top-level `.crs` families include `Template` (1,540), `Dialog` (1,456),
`Models` (1,117), `Game` (1,159), `Material` (269), `Audio` (153), `Terrain` (43), and
`MeshLayout` (19). Counts classify paths by their first directory; they are inventory counts, not
claims about how often a resource is loaded.

All 5,812 compiled-resource entries map to 170 distinct type IDs, each with one class-name
candidate in the current observed schema table at `tools/schema/types.json`. Their file headers
contain 3,984 dependency strings across 1,835 resources. None of those strings exactly matches a
TOC path, including after case folding and replacing a terminal `.rsc` with `.crs`. Many names look
like resource-family references or source assets such as `.wav`, `.fbx`, and shader files; their
resolution/alias rules are still open. These file-header edges are not the same as typed path fields
inside class payloads: for example, the school template's header dependency count is zero even
though its decoded component-description payload references component descriptions.

The type-name string xrefs are in [`GAME-TYPE-STRING-REFERENCES.tsv`](GAME-TYPE-STRING-REFERENCES.tsv).
They were exported from Ghidra 12.1.4 for the Application and Runtime DLL independently with
`tools/ghidra/ExportTypeStringReferences.java`, then combined by
`tools/schema/combine_type_string_references.py`. The 478 rows cover all 170 observed resource
class candidates in both binaries: 169 names are present in at least one image, and 169 have at
least one direct reference. Ghidra reports 307 direct references total, 231 inside defined functions
spanning 228 distinct function addresses. `Font` is the one candidate not recovered as a defined
string data item in either image. Its Runtime function `UI::Font::_TypeName` at `0x180032480`
decompiles to `return "Font"`, so the class-name value is known, while its literal address and
direct data xrefs remain unresolved. References outside functions are kept as data xrefs and are
not treated as registration calls without further evidence.

For the existing Application Ghidra project, export the type-string references with:

```sh
"$GHIDRA_INSTALL_DIR/support/analyzeHeadless" analysis/gameplay-project banished-gameplay \
  -readOnly -process Application-steam-x64.exe -noanalysis \
  -scriptPath tools/ghidra -postScript ExportTypeStringReferences.java \
  /tmp/application-type-strings.tsv tools/schema/types.json
```

The Runtime DLL was imported and analyzed in the ignored local project
`analysis/runtime-identity-project/banished-runtime`, then the same post-script was run with
`-readOnly -process Runtime-steam-x64.dll -noanalysis`. Combine both exports with:

```sh
python3 tools/schema/combine_type_string_references.py \
  docs/GAME-TYPE-STRING-REFERENCES.tsv \
  /tmp/application-type-strings.tsv /tmp/runtime-type-strings.tsv
```

## Identity layers

Keep these keys distinct when documenting a finding:

| Key | Stable meaning | Example / current source |
|---|---|---|
| Package path | Name used to locate an entry within `.pkg` data | `Template/SchoolHouse_resource.crs` in the inventory |
| Package offset | Byte position of that entry in one exact package file | `package_offset` column; only meaningful with that package's hash |
| Resource type ID | Serialized four-byte class/type identifier | Parsed from a `.crs` header, then cross-checked against the unique name candidate in `tools/schema/types.json` and registered class factories |
| Resource field/reference | Path or typed reference serialized inside another resource | School template → `attendance`, `workplace`, and other descriptions |
| PE virtual address | Stable location in a specific shipped binary image | e.g. `Application-steam-x64.exe:0x140116d10`, keyed by binary SHA-256 |
| Type-name string VA | Address of a defined resource class-name string inside one PE image | `Application-steam-x64.exe:0x140168e58` contains `ComponentDescription`; direct xrefs are listed in the type-string TSV |
| Runtime object pointer | Process-local address of an allocated object | Only meaningful for the process/session and object lifetime where observed; not yet inventoried globally |
| String literal | Text stored in a binary or resource | PE address in `analysis/export/Application-steam-x64.exe/strings.txt`, or resource-relative string field |

An address such as `0x140116d10` is not a package pointer, and a path in a resource is not a C++
symbol. Ghidra global data labels (for example `DAT_1401cf...`) should be linked to a recovered
type registration or table before assigning a semantic name. Runtime pointers need an object type,
owning entity, field offset and observation lifetime before they can be treated as identities.

## First mapped family: school and citizen

The resource inventory now provides the complete path namespace. The first cross-layer mapping is
the school attendance chain in [SCHOOL-ATTENDANCE-TRACE.md](SCHOOL-ATTENDANCE-TRACE.md):

`Template/SchoolHouse_resource` → `SchoolHouse_workplace` →
`Game/Profession/Profession.rsc:teacher` and `SchoolHouse_attendance` → citizen description's
teacher reference → citizen slot `+0x208` → CitizenAI action 10 (`0x140112a30`) → typed
CitizenComponent message code 4 → vtable `0x1401689a0` slot 15 → education progress and UI/output
threshold. This links the serialized resource identity to an AI action, message constructor and
dispatcher, and receiving component vtable; detailed field-level evidence is in the school trace.

Other verified identity links already documented:

* [ENTITY-COMPONENT-LIFECYCLE.md](ENTITY-COMPONENT-LIFECYCLE.md) maps resource paths to registered
  runtime component types, factory callbacks, owner pointers, description pointers and lifecycle
  slots.
* [RESOURCE-PRODUCTION-FLOW.md](RESOURCE-PRODUCTION-FLOW.md) maps production/workplace type
  registrations to work callbacks and storage-ledger fields.
* [SHIPPED-PRODUCTION-RECIPES.md](SHIPPED-PRODUCTION-RECIPES.md) identifies shipped output and input
  resources by their serialized paths and labels.

## Mapping procedure and open coverage

Some initial type-name links are now concrete:

| Resource class | Serialized type ID | Application string address | Direct-reference function |
|---|---:|---:|---|
| `ComponentDescription` | `0x9ae409dc` | `0x140168e58` | `0x140154910` |
| `CitizenDescription` | `0xe16728ca` | `0x140168978` | `0x140154650` |
| `WorkDescription` | `0x5f0cd0b6` | `0x14016aff0` | `0x140155cd0` |
| `AttendanceDescription` | `0xb6616772` | `0x14015ed90` | `0x1401505c0` |

These rows connect the serialized class ID to a literal string address and a referencing function;
the function's detailed registration role still needs call-site verification before assigning it a
stronger semantic label. Runtime type strings also have engine-symbol references such as
`Runtime-steam-x64.dll:0x180159b80` (`TextDescription`) from
`UI::TextDescription::_TypeName` (`0x180042590`) and `UI::TextDescription::TypeName`
(`0x1800425d0`).

For each resource family, record: exact package path and package hash; serialized type ID and
version; header dependencies separately from payload references; the type registration/factory; serializer field offsets;
code references to the loaded object; and, only when relevant, the runtime owner/slot lifecycle.
For strings, preserve the exact spelling, encoding, containing resource or binary address, incoming
references, and whether the string is a display label, resource path, key, or diagnostic. Each
semantic claim should link both a data source and a code path where possible.

The inventory is the base layer, not complete identity coverage. Resource payloads still need to be
classified and linked, most Ghidra addresses remain unnamed, global pointer tables remain partly
unresolved, and runtime object identities have not been enumerated. The supplied saves now have a
reproducible external-reference index and package-path crosswalk in
[SAVE-REFERENCE-IDENTITIES.md](SAVE-REFERENCE-IDENTITIES.md); serialized object records and their
reference-bearing fields still need to be decoded.
